# Verifying the analog block: strategy, tests, and what the numbers say

The analog block (`analog/`, ring slot 7) is a current-starved ring
oscillator with an 8-bit current DAC. This document says how it was
simulated beyond the typical-corner sweep in `analog/README.md`: over the
PDK's process corners, under Monte Carlo variation, and with device noise;
block by block first, then the whole thing. The tables the tests produce are
in [analog_verification_results.md](analog_verification_results.md)
(generated by `make -C analog verify`, about an hour on 14 cores); the
figures are `verify_*.png` in this directory. The layout side of the same
story is [analog_layout_notes.md](analog_layout_notes.md).

## 1. What "robust" has to mean for this block

The block is an instrument's sensor, not a clock. Nobody needs it to run at
a particular frequency; the tile measures whatever frequency it runs at and
reports the number. So the questions are not "is it within spec" but:

1. **Does it oscillate, and stop, everywhere?** At every process corner,
   supply and temperature the tile will meet, the ring must run when
   enabled and hold when disabled, at every code.
2. **Is the code-to-frequency map monotonic?** The instrument sweeps the
   code; a step where more code gives less frequency would be reported as
   silicon behaviour when it is a design artefact. Monotonicity under
   *mismatch* is the property that binary-weighted DACs are known to lose.
3. **How far does the scale move?** Over PVT and from die to die, so the
   bench knows what range to expect and the tile's divider tap can be
   chosen (the divided ring must stay under 250 MHz, `constraints.md`).
4. **Is thermal noise below the resolution?** The 8-bit control is
   meaningful only if noise on the bias moves the frequency by much less
   than one code step, and the period jitter must be small against the
   counter's ±1 count.
5. **Is every block doing its own job?** A whole-block transient can hide a
   weak block behind a strong one. Each block is tested on its own, with
   ideal sources around it, before the whole thing.

Everything below is "not overboard" by intent: enough to answer those five
questions with numbers and to show where the margins are thin, not a
characterisation report.

## 2. What is simulated, and against what

**Two netlists, both proven against the layout.** The block tests run on the
xschem sub-sheets (`analog/xschem/csro_*.sch`), netlisted as subcircuits
by `verify/netlist_blocks.py`. Those sheets are the drawing that
`make lvs-sch` proved equal to the GDS, so a test on a sheet is a test on
the block as laid out, and each block can be driven with ideal sources. The
whole-block tests run on `spice/tt_analog_ring.spice`, the finger-by-finger
netlist the layout generator wrote and `make lvs` matched against the GDS.
No hand-edited netlist is simulated anywhere.

**Models.** The PDK's PSP 103.6 models via `cornerMOSlv.lib`:

| section | what it is | used for |
|---|---|---|
| `mos_tt`, `mos_ss`, `mos_ff`, `mos_sf`, `mos_fs` | the five process corners | every corner run |
| `mos_tt_mismatch` | typical, plus a random Vt and mobility offset per device instance, `agauss` scaled by 1/sqrt(WL) (`sg13g2_moslv_mismatch.lib`), enabled per device by `mm_ok=1` | local mismatch Monte Carlo |
| `mos_tt_stat` | typical, plus one random draw of the global model parameters per run (`sg13g2_moslv_stat.lib`) | process (die-to-die) Monte Carlo |

Each Monte Carlo sample is a separate ngspice process with its own
`.option seed`, so the runs are independent, reproducible and parallel.
ngspice `.noise` gives the PSP thermal and flicker noise at an operating
point; ngspice has no device noise in transient, which shapes the noise
tests (section 4).

**The PVT box.** 5 process corners x 3 temperatures (-40, 27, 125 C) x 3
supplies (1.08, 1.20, 1.32 V) = 45 points. The three the tile's STA signs
off at (tt 27 C 1.20 V, ss 125 C 1.08 V, ff -40 C 1.32 V) are shown in
full in every table; the other 42 appear as extremes.

**One `.dc` for all 256 codes.** The code is eight digital inputs. Eight
B-sources turn a single swept voltage into the code bits
(`bit k = floor(c/2^k) - 2 floor(c/2^(k+1))`), so one DC analysis walks
every code of the DAC or the bias chain in one process. That is what makes
200-sample Monte Carlo over the full code range affordable.

**Transients sized per code.** The whole block runs from 3.8 MHz to
332 MHz. Every transient is held with `enable` low for two nominal periods,
released, run for 40 nominal periods and measured over the last 16, with
the time step at 1/150 of the nominal period. Every code therefore gets the
same number of cycles at the same resolution, the start-up time comes for
free, and a run takes seconds rather than the minutes a fixed 3 us window
costs at high codes.

## 3. The tests, block by block

Each test is one script in `analog/verify/`; each writes a CSV and a
Markdown table into `analog/out/verify/`, which `verify/report.py`
assembles into the results document.

### DAC (`dac.py`) - csro_dac: 255 weighted fingers + 2 always-on

Sinks from an ideal source holding the drain at 0.6 V (the middle of the
range the real diode node spans), so the array is measured by itself:
how well 2^k fingers deliver 2^k unit currents.

- **Corners:** I(code) at all 45 PVT points. Unit current, code-0 current,
  full scale, endpoint-fit DNL and INL, monotonicity.
- **Mismatch Monte Carlo, 200 samples:** every finger with its own random
  offset. Worst DNL per sample and where it lands (always a major carry:
  code 128, 64, 32 ...), count of non-monotonic samples, spread of the unit
  current.
- **Process Monte Carlo, 100 samples:** spread of the unit current, i.e. of
  the whole scale.
- Also: the array at drain voltages 0.46 and 0.85 V (the diode node at code
  255 and code 1), to show how much the triode units follow their drain.

### Bias chain (`bias.py`) - DAC + MPD diode + MPM mirror + MND diode

Plus eleven replicas of each stage's starve device (PMOS on `vbp`, NMOS on
`vbn`) with drains at mid-rail: the current each stage's starve device
passes while the stage switches, which is what sets the ring's delay.

- **Corners:** `vbp`, `vbn`, I_dac and the per-stage currents against code
  at all 45 points. This is where the compression is visible, and how far
  the bias points move over PVT.
- **Mismatch Monte Carlo, 200 samples:** the spread of the eleven stage
  currents within a sample (the stages are single 1 um and 0.5 um fingers,
  the smallest devices in the block that matter), and the MPD/MPM mirror
  ratio.
- **Noise:** `.noise` at `vbp` and `vbn` with the code held, integrated
  over 1 kHz-1 GHz and 1 Hz-1 GHz, at codes 1, 16, 128, 255, expressed as
  a percentage of one code step of the same node.

### Stage (`stage.py`) - csro_stage: one starved inverter

Driven by and loading identical stages, biased by the real bias chain.

- **Corners:** tPLH, tPHL, output slew at codes 0, 16, 128, 255, all 45
  points; and 1/(11 x (tPLH + tPHL)), the frequency an 11-stage ring of
  these would have, to compare with the whole block.
- **Noise to jitter:** the stage held at its trip point (found by a `.dc`
  sweep in the same run), `.noise` on its output, integrated; divided by
  the output slope at the half-rail crossing from the transient. That is
  the timing jitter of one transition, sigma_td = v_n / (dV/dt), the
  standard small-signal estimate for a ring stage. Twenty-two uncorrelated
  transitions make a period, so period jitter is sqrt(22) larger, and a
  reciprocal count of N periods averages it by sqrt(N).

### NAND (`nand.py`) - csro_nand: the enable gate

- **Hold:** `a` (enable) low, `b` (feedback) swept over the full rail, the
  output's minimum, at all 45 points and three codes. The stopped ring
  must not twitch.
- **Gate:** `a` high, delay as the eleventh inverter, compared with a
  stage's delay at the same code and corner.

### Output buffer (`buffer.py`) - csro_inv + the 2/1 um inverter

A 332 MHz input with 100 ps edges into 15 fF and into 108 fF (the
Liberty's `max_capacitance`), all 45 points: high and low levels reached,
20-80 % rise and fall, delay.

### Whole block (`ring.py`) - spice/tt_analog_ring.spice

- **Corners:** f(code) at codes 0, 1, 2, 4, 8, 16, 32, 64, 128, 255, all 45
  points; supply current running and disabled; clk_out level while
  disabled; start-up time; monotonicity at every point; supply pushing
  (%/V) and temperature coefficient (ppm/C) at the typical corner.
- **Mismatch Monte Carlo, 64 samples:** f at codes 0, 15, 16, 127, 128,
  255. The two major carries are where a binary DAC can go non-monotonic;
  the count of samples with f(16) <= f(15) or f(128) <= f(127) is the
  answer to question 2 for the whole block.
- **Process Monte Carlo, 32 samples:** f(0), f(16), f(255) and the span
  f(255)/f(0).
- **Noise, transient:** the bias node's current noise density is measured
  by `.noise` (with the node's impedance from an `ac` at the same operating
  point) and injected back as a `trnoise` current source of that density
  while the ring runs 600 periods. Period jitter and the jitter of 50-period
  means are read from the edge times. The same run without the source gives
  the simulator's numerical floor, reported beside it.

### Post-layout (`make pex`, `make sim-post`, `make verify-ring-post`)

kpex (2.5D) extracts the parasitic capacitances of the flat macro against
its LVS netlist; `layout/build_sim_post.py` rewrites the result so ngspice
can run it in the pre-layout netlist's place (same subcircuit, same ports;
the labelled internal nets keep their names). Then:

- **Attribution** (`verify/pex.py`): the capacitors sorted by net and by
  block - DAC and code buses, bias nodes, ring stage outputs, enable,
  output buffer - beside the device capacitance each net already carries.
  A flat layout has no block cells to extract one by one; its nets are
  labelled, so a block is a group of nets and gets its own number.
- **The same circuit twice**: the macro pre and post layout at typical,
  codes 0, 16, 128, 255, with the block-level quantities read off the
  running ring's internal nodes: every stage's delay, the NAND's, the
  buffer's, the ripple the ring induces on `vbp` and `vbn`, and the RC
  settling of a code bus driven through 500 ohm.
- **The whole-block run again** on the extracted netlist: all 45 PVT
  points, Monte Carlo and noise, exactly as pre-layout.
- **The environment run again** (section below) on the extracted netlist.
- **The shipped Liberty** (`make lib-post`) is characterised on the
  extracted netlist, so the code pins' capacitance includes their buses.

kpex 2.5D extracts capacitance only. Metal resistance (the DAC's 0.3 um
Metal1 bars carrying tens of microamps, sub-millivolt drops) is argued in
`analog_layout_notes.md` rather than simulated.

### Environment (`make verify-env`, `make verify-env-post`)

The tile around the macro, built as sources (`verify/environment.py`):
50 MHz square ripple of 10, 30 and 100 mV peak-to-peak on VPWR; 10 mV rms
broadband random noise on VPWR; a 50 mV supply step mid-run; 30 mV
peak-to-peak ground bounce; a full-swing 50 MHz aggressor coupled through
20 fF onto `code[0]`, `code[7]` and `enable` (the victims driven through
500 ohm, as the tile's buffers would) and through 30 fF onto `clk_out`;
and a 5 ns `enable` edge. Each case runs 300 periods at codes 16 and 255
against a quiet reference, and reports the mean frequency shift (what the
counter reads), the period jitter, the jitter of 50-period means, and for
the enable and output cases whether the stopped ring stays stopped and
whether extra edges appear at the divider's threshold. The amplitudes are
worst-case for a 1.2 V digital tile on a shared supply; the results are
bounds, and the supply-pushing number from the corner run says how to
convert any measured shift back into a supply excursion.

## 4. What is approximate, and what is not covered

- **Noise in transient is injected, not intrinsic.** ngspice has no device
  noise in transient analysis. The whole-block jitter run injects the
  white part of the measured bias-node current noise; the stage's own
  thermal jitter is estimated analytically from its `.noise` and slope.
  Both are standard small-signal estimates; together they bracket the
  jitter, they are not a transient-noise simulation.
- **Flicker noise** appears in the `.noise` results (the 1 Hz-1 GHz vs
  1 kHz-1 GHz columns) but is not injected into the transient: below
  10 MHz the bias node's own time constant turns it into slow drift, which
  a reciprocal count over 200 periods averages and a bench repeats.
- **Systematic mismatch** (stress, well proximity, the partial rows of the
  small DAC bits) is not in the PDK's models and therefore not in the Monte
  Carlo. The random DNL results carry margin for a systematic component of
  the same size; see `analog_layout_notes.md`, section 4.
- **Parasitic extraction is capacitance only** (kpex 2.5D), from a
  2.5D model of the BEOL stack, not silicon-correlated. It changes the
  answer a lot for this block (section 5): the ring's wiring is comparable
  to its minimum-size devices. Resistance is not extracted.
- **The environment model is sources, not the tile.** Ripple, bounce and
  crosstalk are injected at chosen amplitudes; nothing here simulates the
  digital netlist's actual current profile or the real routing next to the
  macro's pins. The amplitudes are chosen high, and the pushing number from
  the corner run turns any measured shift into an equivalent supply
  excursion.
- **The Liberty file** is characterised at the typical corner only. The
  macro has no timing arc (clk_out is a clock source), and its input
  capacitances are gate capacitances, which move little with corner.

## 5. Reading the results

The numbers below are from `analog_verification_results.md` as generated
on 2026-09-07 (200 mismatch and 100 process samples for the DAC, 200 for the
bias chain, 64 and 32 for the whole block). Against the five questions of
section 1:

**1. It oscillates, and stops, everywhere.** At all 45 PVT points and all
ten codes the ring runs after release, and with `enable` low `clk_out`
sits at the rail (never below 100 % of VDD at the operating point or during
the hold, at every point) while the NAND's output stays above 99.9 % of VDD
over a full-rail sweep of the feedback. Start-up from release to first edge
is at most 230 ns (slow-hot-low corner, code 0; 2 ns at code 255), far
inside the time between a host's `RING_SEL` and `START` writes. The output
buffer reaches both rails into the Liberty's 108 fF at every corner, with
20-80 % edges of 400 ps at worst.

**2. The map is monotonic.** In code, at every one of the 45 PVT points.
Under mismatch, 200 of 200 DAC samples are monotonic with a worst DNL of
-0.39 LSB (at code 128, as expected of a binary array: the worst step is
almost always the 127-128 carry, then 63-64), and 64 of 64 whole-block
samples keep both major-carry steps positive. The smallest whole-block
step seen is f(128) - f(127) = 0.13 MHz against a mean of 1.2 MHz: the
128 carry is where the margin is thinnest, about 1.5 sigma from a
non-monotonic sample at this sample size. The layout keeps every finger
identical for exactly this reason (`analog_layout_notes.md`, section 4),
and this is the number to compare against the measured 127-to-128 step on
silicon; systematic effects the models do not carry would show up there
first.

**3. The scale moves by about three.** Over the whole PVT box the frequency
at any code spans a factor of 2.75 to 2.96 (code 255: 184 MHz at
ss/125 C/1.08 V to 544 MHz at ff/-40 C/1.32 V; typical 332 MHz). The stage
delay alone spans 2.8 to 3.0, so the ring is the stage: the bias chain's
per-stage current spans 3.7 to 4.0 and the stage's own delay saturates
part of that. Die to die (process Monte Carlo) the sigma is 5.3 to 5.7 % of
frequency at every code, with f(255)/f(0) between 76 and 93. Supply
pushing is large and code dependent, 64 %/V at code 16 rising to 155 %/V at
255 (the DAC's triode units follow the supply through the diode); the
temperature coefficient is -3900 ppm/C at code 16 and -2100 ppm/C at 255.
None of this is a defect - it is a trimmable ring, and characterising it is
the instrument's purpose - but it fixes the tap rule: the divided ring
must stay under 250 MHz, so tap 3 is safe for this ring everywhere.

**4. Noise is below the resolution, with one term worth watching.** Three
noise paths were quantified:

- *The stages' own thermal noise* (small-signal estimate): 1 ps rms per
  transition at code 255, 35 ps at code 16, 680 ps at code 0; as a fraction
  of the period 1600 to 14000 ppm rms per period, averaged by a 200-period
  count to 120 to 1000 ppm. At code 0 this is a conservative bound: it is
  dominated by flicker noise integrated from 1 kHz, which does not average
  as sqrt(N).
- *White noise on the bias node*, injected into a 600-period transient:
  period jitter of 10 ps at code 16 (370 ppm) and 0.8 ps at 128 (180 ppm),
  falling to 45 and 27 ppm on 50-period means. The quiet reference run puts
  the numerical floor at 5 to 7 ppm, so these are the noise.
- *Slow (1 kHz-1 MHz) noise on the bias nodes*, which acts as a code error
  within one measurement rather than as jitter: 110 to 125 uV rms on `vbn`
  at every code, 14 uV on `vbp`. Against one code step of the same node
  that is 1 % of a step at code 1 but 28 % at code 255 on `vbn` (2.4 % on
  `vbp`), because the step shrinks with code while the noise does not.
  Since roughly half the stage delay follows `vbn`, this is about a tenth
  of an LSB of frequency at the top codes: repeatable measurements will
  scatter by a few hundred ppm there. It comes from the flicker noise of
  the two small mirror devices MND and MPM (0.5 and 1 um fingers); making
  them larger is the noted fix.

The instrument's own resolution is ±1 count: 1/241 = 4100 ppm on the 200
period, tap 3, code 255 measurement in the datasheet example. Every noise
term above is below it. A longer window (higher `TARGET_N`) buys
resolution until the slow bias noise, at a few hundred ppm, becomes the
floor.

**5. Each block does its job.** The DAC's weighting is ideal by
construction (DNL 0.000 at every corner with the drain held; the current
follows the drain by ±10 % between 0.46 and 0.85 V, which is the
compression the bias chain shows). The bias chain delivers 41 to 47 times
the stage current into the diode against the nominal 48 (the two devices
sit at different drain voltages), and under mismatch the eleven stage
currents differ by 1.7 % rms at code 255 and 7.4 % at code 1 (PMOS side;
the NMOS side 5 and 19 %) - visible as duty-cycle asymmetry, second-order
in frequency. The NAND is 1.14 to 1.24 times slower than a stage at every
corner, one slightly slow stage of eleven. The stage-based prediction of
the ring frequency (1 / 22 delays) runs 8 to 15 % above the whole-block
transient at every corner, the difference being the NAND and the buffer's
load on stage 10.

**6. Post-layout: the parasitics are not negligible, and nothing breaks.**
kpex finds 721 fF of parasitic capacitance in the macro. Two thirds of it
is on the DAC's code buses and `vbp` bars, where it adds 16 to 90 % to
gate loads that are DC controls (bus settling through a 500 ohm driver goes
from 1.5 to 1.8 ns on `code[7]`); the shipped Liberty carries the new pin
capacitances. The part that matters is small in absolute terms and large in
proportion: each stage output carries 1.7 fF of wiring against about 1 fF
of device, so every stage delay doubles and the ring runs at half its
pre-layout frequency at every code and corner (2.0 / 18 / 105 / 164 MHz at
codes 0 / 16 / 128 / 255, typical; 90 to 275 MHz at code 255 over the
signoff corners). The pre/post figure is `analog_ring_sim_post.png`. The
ring-induced ripple on the bias nodes roughly doubles to 1.6 mV on `vbp`
and stays at 5 to 8 mV on `vbn`. The post-layout corner, Monte Carlo and
noise runs (appendix, "ring_post") repeat the pre-layout conclusions with
one exception worth stating plainly. Monotonic in code at all 45 PVT
points; the stopped ring holds everywhere; start-up is at most 430 ns
(slow-hot-low corner, code 0); die-to-die and mismatch spreads are the
same in relative terms (2.1 % sigma at code 255 under mismatch, span
f(255)/f(0) 75 to 89); the injected bias noise gives 14 ps of period
jitter at code 16 and 1.3 ps at 128, 47 and 14 ppm on 50-period means.
The exception: **one of 64 mismatch samples has f(128) below f(127)**, by
0.12 MHz against a mean step of 0.58 MHz (the pre-layout run had 0 of 64
with a 1.2 MHz mean step). The parasitics halved every frequency step
while the random current mismatch of the DAC's fingers did not shrink, so
the 127-128 carry sits about 1.2 sigma from a reversed step: expect a
percent or two of dies to show a small non-monotonic step at that one
code, of the order of 0.1 % of the frequency. For the instrument that is
a measurable feature of a binary DAC, not a fault (the code-to-frequency
map is measured anyway), and the fix for a second version is the one the
digital design's notes already anticipated: thermometer-code the top two
bits, or add dummies and a common-centroid row order. The RTL model, the
cocotb tests, the tile's constraints and the datasheet numbers were all
moved to the post-layout values; the divider's tap rule only gets easier.
The lesson for the layout is in `analog_layout_notes.md`: the minimum-size
inverters should have been two to three times wider.

**7. The tile around it: bounded, and one number to remember.** Injected
supply ripple, ground bounce, random supply noise, a supply step and
crosstalk onto every pin, pre and post layout (appendix, "env" and
"env_post"):

- *Supply is the sensitivity.* A 50 mV step moves the frequency by 3.4 to
  3.9 % at code 16 and 7.8 to 7.9 % at code 255, within tens of ns, as the
  static pushing predicted; there is no loop filter, the ring follows the
  supply at once. A 50 MHz ripple shifts the *mean* frequency by tens of
  ppm at 10 mV p-p, 140 to 350 ppm at 30 mV and 0.16 to 0.4 % at 100 mV
  (the counter reads the mean; the shift is the curvature of f against
  VDD), and adds 35 to 130 ps of cycle-to-cycle jitter at 30 mV, which the
  reciprocal count averages to a few ps over 25 periods. 10 mV rms of
  broadband supply noise: +50 to +500 ppm and 10 to 30 ps of jitter. 30 mV
  p-p ground bounce: -140 to -350 ppm, 30 to 130 ps jitter. So: measure
  with the digital side quiet (only the reference clock running, the code
  changed between measurements), and expect a few hundred ppm of
  supply-driven scatter otherwise. The pushing number converts any
  observed shift back into millivolts.
- *The inputs do not care.* A full-swing 50 MHz aggressor through 20 fF
  moves a code gate by 33 to 60 mV around its rail and the frequency by
  under 30 ppm; onto `enable` it dips the running ring's enable to 1.14 V
  (under 80 ppm) and, with the ring stopped, lifts enable to 60 mV: the
  ring stays stopped. A 5 ns enable edge starts the ring cleanly with no
  short early period.
- *The output is the one thing to route with care.* `clk_out` drives 15 fF
  through a 2 um / 1 um inverter. Aggressor coupling of 5, 10 and 20 fF
  leaves it clean at both codes on both netlists (undershoot to -0.1 V,
  no extra edge at the divider's 0.6 V threshold); at 30 fF the
  post-layout run at code 16 shows one extra edge per run (the dip crosses
  the threshold; pre-layout it stopped at 0.17 V short). 30 fF is an
  aggressor running beside `clk_out` at minimum spacing for a few hundred
  microns; the hardened tile's route to the mux is tens of microns and
  the flow's routing keeps other nets off the macro. It is nevertheless
  the sharpest edge in this block: a second version would give the output
  buffer a wider last stage.

**What would change the design, in order:** wider stage inverters (the
post-layout halving); thermometer coding of the top DAC bits, or dummies
and a common-centroid row order, for the 127-128 carry (1 of 64 post-layout
samples reverses it); larger MND/MPM for the bias flicker noise; a wider
output stage against crosstalk; a cascode on the DAC output for the
compression and the supply pushing. None of them is needed for the block
to do what the tile asks of it.
